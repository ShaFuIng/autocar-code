## 2. 可重用接口

### 現在就能用（今天每一輪都在用，實測）
都在 Orin `192.168.0.244:8000`（orin-dashboard，需登入；`server.py`）：

| 接口 | 用途 |
|---|---|
| `GET /api/status` | 控制板狀態：`state`（LOCKED／READY／MANUAL…）、`reason`（REMOTE_STOP／PHYSICAL_ESTOP…）、馬達指令、I²C 錯誤數、舵機設定、急停腳位 `pins.D11` |
| `GET /api/pid/status` | 模型與輪次狀態、本輪參數、版本、各模組回報 |
| `GET /api/pid/frame` | 目前的辨識／路徑預覽圖（JPEG）；另有 `/camera.jpg` |
| `POST /api/pid/prepare`、`/api/pid/start` | 載入模型、開始一輪。開始時要帶完整 PID 參數與 `execution_mode` |
| `POST /api/pid/stop` | 停止本輪 |
| `POST /api/pid/preview-stop` | 卸載模型（要帶 JSON 內容 `{}`） |

`execution_mode: "orin_timed"`：Orin 接受後獨立跑到 `seconds` 到期，不靠瀏覽器心跳（`live_pid.py` 第 528～606 行）。**「沒有時間限制」可以用很大的 `seconds` 達成**，不需要舊 07。

### 舊 07 接口：程式還在，但不能直接用
`/api/ops07/status|load|arm-hold|release|pause|resume|stop|reset`（`server.py` 第 596、694～706 行 → `ops07_runtime.py`、`ops07_route.py`）仍在車上，但：

- `orin_continuous` 模式只接受 07 的 arm-hold 發出的票，而且會核對權重等於 07 方案包（`live_pid.py` 第 530、543 行）；方案包是 11-07～11-08 的三個舊包。
- 接續用的 `apply_seed()` 只會設定 `track_pos`（舊定位）、`curve_map`、`DashRoute`；**現在所有路段控制靠的是 `lap_pos`，它沒有被設定**。
- 暫停後校正時鐘的 `rebase_route()` 清單裡沒有 11-12 之後新增的模組：`lap_pos`、`arc2`（路口保持、落地）、`lap_ff` 帶狀、`lap_speed`、`brake_zones` 的圈內錨點、`i_ramp`、彎 4 出彎修正。

所以舊 07 的暫停／接續／任意起點**與現在的車不相容**（由程式內容判斷，沒有實車試過）。可以借用的是它的寫法：`read_go()` 與 `poll_flag()`（讀場地訊號）、`atomic_json()`（原子存檔）、`LapClock`（計時）。

## 3. 任意位置接續

### 唯一定位來源：`lap_pos`
- 內容：`anchor`（最近通過的地標）＋ `since_anchor_m`（通過後走了幾公尺，編碼器算，約 5 Hz 更新）＋ `seg`（路段名）＋圈次。
- 地標順序：起點 → C1s／C1e（彎 1 起訖）→ C2s／C2e → C3s → RAMP（坡腳）→ TOP（坡頂）→ DASHe（虛線轉彎結束）→ DOWN（開始下坡）→ LAND8（落地）→ C4e（彎 4 結束）。
- 地標是車**實際開過**時由陀螺儀轉角、俯仰等判定的，沒有「直接指定現在在哪」的入口。
- **沒有** snapshot／restore／seed 能力。最小新增點是 `lap_pos.py` 加一個設定入口，再讓下列模組各自能從中途初始化。

### 各模組在中途開始時缺什麼
| 模組 | 中途開始的問題 |
|---|---|
| `lap_speed`、`brake_zones` | 油門區與上限區都掛在本圈的地標上；沒通過地標就不生效（`brake_zones` 會退回以起點計的備援區，位置不對） |
| `arc2` 路口保持 | 參考方向取自進區前 1～4 m 的直線航向；路口前才放車就沒有參考 |
| `lap_ff` 帶狀（彎 2、彎 4） | 以彎前直線的航向為 0 度來算已轉角度；彎中開始不知道已轉幾度 |
| `curve_map` | 靠陀螺儀累積轉角判斷彎的進度；彎中開始會少算 |
| `DashRoute`、上層 | 靠「爬坡→到頂→轉彎」的順序推進；上層開始沒有前面的狀態 |
| 落地控制 | 靠下坡俯仰與 DOWN／LAND8 地標；坡上開始可行性未知 |
| PID 積分、間隙補償 | 重新起步時歸零即可，這兩個不是障礙 |

### 依官方地圖逐段（01～12 不重新編號）
| 位置 | 現況 |
|---|---|
| 旗子起點 | **可直接支援**（今天每一輪都是） |
| 01～02（彎 1）之前的主直線 | 需新增初始化；風險最低，因為後面馬上會通過彎 1 的地標 |
| 02→03 斜線、03～04（彎 2）、04→05 | 需新增初始化；兩個路口都要先有直線航向參考 |
| 05～09（左彎、彎 3） | 需新增初始化；彎 3 是多段短彎，中途不知道在哪一段 |
| 09 坡道、上層、10 虛線轉彎、下坡 | **目前不可可靠支援**：狀態機必須從坡腳依序推進；上層失敗就是掉下去 |
| 11～12（彎 4） | 需新增初始化（帶狀要已轉角度） |

「不輸入車頭角度」在旗子起點成立（朝規定方向放車即可）。中途位置要成立，至少需要「放在直線段、車頭朝行進方向」這個前提，彎中不成立。

**建議**：這一版只支援「回旗子重新起跑」。途中停車後由人把車放回起點再開始；本場進度（已完成圈數、時間）由手機頁／服務保存即可，這部分不需要動車控。

## 4. 手機直連方案

### 網路（實測，11-20 18:3x）
- Orin 目前連的是場地 Wi-Fi，連線名稱 `Orin-R18-AIRACE`，位址 `192.168.0.244`（DHCP，會變）。
- **從 Orin 讀場地訊號是通的**：`http://192.168.0.149:8080/go` 回 HTTP 200、內容 `0`、耗時 0.085 s。筆電先前逾時的原因未查，但車端這條路是通的。
- orin-dashboard 只在 `192.168.0.244:8000` 監聽，需登入。Android 連同一個 Wi-Fi 就能開 `http://192.168.0.244:8000`。Android 多半解不了 `orinnano-super.local`，要用 IP；位址變了要有辦法查（例如車端開機時顯示或固定 DHCP）。

### 做法建議：另開一個小服務，不動車控
比照既有的影子頁（`orin-shadow.service`，連接埠 8091），在 Orin 上新增一個獨立的手機頁服務（例如連接埠 8092）：

- 只提供手機版網頁，並把操作轉給 `8000` 的既有接口；**不修改、不重啟 orin-dashboard**。
- 開跑參數（今天的 PID 文件 rev152 內容＋`execution_mode: orin_timed`＋很大的 `seconds`）存成 Orin 上一個固定檔案，由這個服務送出；手機頁不提供任何參數調整。
- 登入沿用 8000 的登入，不另存密碼。
- 「等待場地統一起跑」放在這個服務裡：每 50 ms 讀 `/go`、先看到 0 再看到 1 才送開始、之後停止輪詢。延遲是 Orin 本機呼叫，不經手機。
- 手機鎖屏或斷線不影響行駛（`orin_timed` 本來就不靠瀏覽器）；重新連線只讀狀態、不重送指令。
- 停止鍵直接打 `/api/pid/stop`，並顯示「是否收到回覆」；實體急停照舊保留。

### 控制權
筆電工作台與手機頁同時開著時，兩邊都能送開始／停止。精簡版的處理：手機頁顯示「目前有輪次在跑，run id 與開始時間」，有輪次時不給開始鍵。比賽時筆電不開工作台最單純。

### 圈時
車端每格都有 `lap_pos` 的圈次與路段；彎 1 起點（C1s）每通過一次算一圈。手機頁顯示「本輪時間」與「每圈時間（以彎 1 為計時點）」即可。從旗子到第一次彎 1 是不完整的第 0 段，需另外標示。

## 8. 需要使用者決定的事項

1. **比賽時場上會不會同時有別的車？** 決定前車功能要不要存在。
2. **比賽要跑幾圈／多久？** 用來設定 `seconds` 的上限（例如 20 分鐘）以及圈時畫面。
3. **途中停車後的規則是什麼？** 是否允許原地接續，還是必須回起點？若規則就是回起點，任意位置接續不用做。
4. **是否採用統一起跑訊號？** 車端讀 `/go` 是通的，但還沒有實作等待邏輯；需要一次假訊號測試與一次現場測試。
5. **比賽當天筆電還在不在場邊？** 若在，手機只當遙控與顯示；若不在，Orin 位址變動時要有查位址的辦法。
6. 這一版是否同意縮成「旗子起跑＋開始／停止＋狀態＋影像＋圈時（＋統一起跑）」。

## 附：今天與手機頁有關的車端事實

- 每輪結束原因目前常見三種：`USER_STOP`（網頁停止）、`STALE_GENERATION`（按了實體急停）、時間到。手機頁需要把這三種翻成中文。
- 實體急停按著時 `/api/status` 回 `state: LOCKED`、`reason: PHYSICAL_ESTOP`、`pins.D11: 0`；放開後才可開始。
- 重啟車控或 Orin 重開機後，模型要重新載入才可開跑；載入約需十幾秒，停止鍵不能排在載入後面。

## 補充（11-20 18:5x）：使用者把最低需求改為「原地暫停後能接著跑」

使用者定調：不需要指定任意起點，但**按暫停後要能從停下來的地方繼續**。這比任意位置接續小很多，評估如下。

### 可行性：可行，但要改車控程式並重啟（未做）
今天查到的程式事實：
- `live_pid.py` 第 1847 行已有一個暫停掛接點（`ops07_support.holding_frame`）：暫停期間影像照樣辨識，但不更新任何路段控制、PID 或路線狀態，輸出固定為「舵量回保存中心、油門 0」。這正是需要的行為；目前只有舊 07 的連續模式會走到它。
- 幾乎所有路段模組（`lap_pos`、`arc2`、`lap_ff`、`lap_speed`、`brake_zones`、`curve_map`、`dash_route`、`speed_adapt`、`i_ramp`、`yaw_inner`、`play_comp`、上層各模組）內部都**不自己讀時鐘**，時間是由 `live_pid` 傳進去的。所以暫停只要把「暫停了多久」從時間裡扣掉（或把各模組記著的時間往後平移），控制狀態就能原樣接上。
- 舊 07 的 `rebase_route()` 就是做這件事，但清單只涵蓋 11-08 以前的模組，要補上之後新增的模組。

### 最小做法
1. 車控加兩個接口：暫停、接續（與舊 07 的方案包無關；`orin_timed` 的到期時間在暫停期間不倒數）。
2. 暫停＝油門 0、舵量回保存中心、控制狀態凍結；**里程（編碼器）在暫停期間照算**，因為按下暫停後車還會滑行一段。
3. 接續＝把暫停時間補回各模組的時間欄位，PID 積分與間隙補償歸零，從靜止重新起步。
4. 故障、I²C 異常、實體急停期間不能接續；實體急停會結束本輪（現有行為），那種情況仍要回旗子重跑。

### 可以離線驗證的部分
用既有的重播工具，在錄好的輪次中間插入一段假暫停（直線、彎中、路口前、坡上、上層、落地各一處），檢查暫停後的每一格指令是否與沒暫停時逐格相同。這能證明「控制狀態沒有因暫停而走樣」。

### 離線驗證不到、要現場試的部分
- 車從靜止重新起步（彎中、路口保持中）是否順；重播裡的車是照原速在動。
- **坡道、下坡、上層**：坡上油門 0 車會倒退或下滑，位置就不對了；上層的轉彎狀態機對時間與車速敏感。第一版建議這三段「暫停可以（一定要能停），但接續前提示需回旗子」，等平地驗證過再放寬。
- 暫停後若車被人搬動，車端無法得知；規則是「暫停期間不要動車」。

### 現場試驗順序（每步需當次授權）
架空輪子按暫停／接續 → 直線上 → 彎 1 彎中 → 路口前 → 彎 4 出彎後；每次看接續後 2～3 m 的走線與是否通過下一個地標。

### 對手機頁的影響
多兩顆鍵（暫停、繼續）與一個狀態「已暫停」；回覆遺失時不可自動重送「繼續」。其餘同精簡版。

## 對「最新定案」（需求文件 18:43 版開頭）的回覆（11-20 19:0x）

**結論：這一版做得到。** 三項都要改車控程式並重啟一次，目前**都還沒實作**；下面的接口是我準備實作的契約，不是現有 API。

### A. 黑白遮罩＋路徑：資料現成，只缺一個讀取接口（實測）
- 車端每一格控制資料本來就帶著 `mask_png` 與 `path`，是 worker 為控制算出來的同一份結果，**不需要為顯示再跑一次 YOLO**。
- `mask_png`：640×360、8 位元灰階 PNG（白＝辨識到的線、黑＝背景），base64 編碼；今天的紀錄裡一張約 1.8 kB。
- `path`：一串 `[x, y]`，座標是 **1280×720** 影像座標；畫在遮罩上要乘 0.5。這是車控實際用來取誤差的那條路徑（已含路口切換後的結果），不是另外算的顯示線。
- 同一筆資料還有 `seq`（控制序號）、`frame_seq`（相機影格序號）、`capture_at`（擷取時間，Orin 的單調時鐘）、`valid`、`path_algorithm`。
- 現有的 `/api/pid/frame` 是「相機原圖＋疊圖」的 JPEG（worker 的 `render_preview`），**不符合**這次的要求，不要用它。

準備新增：`GET /api/pid/mask`
```json
{"run_id": "…", "seq": 146928, "frame_seq": 157537, "age_s": 0.07, "valid": true,
 "mask": {"png_base64": "…", "width": 640, "height": 360},
 "path": {"points": [[1145.7, 328.0], [1122.2, 336.0]], "width": 1280, "height": 720},
 "path_algorithm": "camera-pair-v2-junction-flag", "paused": false}
```
- 只回「目前最新的一格」，不排隊；手機用 `seq` 判斷有沒有新畫面，`age_s` 超過門檻就顯示「畫面未更新」。
- 這個接口只讀記憶體裡已有的資料，在網頁服務的執行緒回應，不進控制迴圈；手機拉得慢只是自己少看幾格。每格約 2～3 kB，手機每秒拉 10 次約 30 kB/s。
- 模型沒載入或還沒有結果時回 503。

### B. 暫停／繼續（準備新增）
- `POST /api/pid/pause`，內容 `{"run_id": "…"}` → `{"ok": true, "run_id": "…", "state": "paused"}`
- `POST /api/pid/resume`，內容 `{"run_id": "…"}` → 成功同上、`state: "running"`；不能接續時回錯誤與原因代碼。
- `run_id` 不是目前這一輪就拒絕（`STALE_RUN`）；重複送同一個暫停或繼續不會產生第二次動作，只回目前狀態。
- 不能接續的原因代碼（手機顯示中文）：`ON_SLOPE`（坡道／下坡）、`UPPER_DECK`（上層）、`FAULT`（車端故障或 I²C 異常）、`ESTOP`（實體急停）、`NOT_PAUSED`、`RUN_ENDED`。坡道／下坡／上層按暫停一樣會停，只是不提供接續，要停止本輪後回旗子重新開始。
- 暫停時：油門 0、舵量回保存中心；影像辨識與 `GET /api/pid/mask` 照常更新；路段控制、路線狀態、PID 全部凍結。
- **滑行**：暫停後里程（編碼器）繼續累加到車停住為止，位置跟著走。若滑行中通過了地標（例如剛好滑過彎道起點），因為判定地標靠的是陀螺儀與俯仰、暫停時也照常讀取，位置會正常推進；但依賴「彎前直線航向」的模組可能沒取到參考，這種情況第一版回 `resume` 錯誤、請使用者回旗子（原因代碼另訂 `MOVED_ACROSS_SEGMENT`）。實際多常發生要現場看。
- 繼續時：補回暫停時間、PID 積分與間隙補償歸零、車速相關的平滑量重設，從靜止起步。**不恢復**暫停前的舵量與油門。

`GET /api/pid/status` 會多一段：
```json
"pause": {"state": "running|paused", "since_s": 12.3, "can_resume": true, "reason": null, "coast_m": 0.42}
```
圈時：暫停時間不計入圈時與本輪行駛時間（兩者都另外給「含暫停」的總時間）。

### C. 沒有時間限制
- 現有 `orin_timed` 一定要給有限的 `seconds`（`live_pid.py` 第 534 行），到期會停；所以**現役模式是限時的**，今天每輪都用 500 s。
- 最小改動：`/api/pid/start` 允許 `"seconds": null`（只在 `orin_timed`），表示沒有到期時間；其餘停止條件（網頁停止、實體急停、Orin 本地影像過期／丟線、控制故障）不變。這是程式改動，和 B 一起做。
- 在這個改動上車前，手機頁若要先測，只能用有限秒數，而且畫面要照實顯示剩餘時間。

### D. 開始與載入（沿用現有）
- 載入模型：`POST /api/pid/prepare`；開始：`POST /api/pid/start`（帶固定參數檔的內容、`execution_mode: "orin_timed"`、`seconds`）；停止：`POST /api/pid/stop`；卸載：`POST /api/pid/preview-stop`（內容 `{}`）。
- 固定參數檔＝今天筆電工作台 PID 文件 rev152 的內容（`center_us` 1490）。凍結跑車版時我會把它和快照一起交付，放在 Orin 上給手機服務讀。
- 確切的請求欄位我會在實作完成時附上實際抓到的範例，不在這裡憑記憶寫。
